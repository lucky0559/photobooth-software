# iPad Safari trial implementation plan

Date: 2026-11-22  
Branch: `feat/ipad-web`, based on the paired print work  
Design: [iPad trial web app](../specs/2026-11-22-ipad-web-design.md)

Deliver `apps/kiosk/dist-web/` as a static HTTPS build and `docs/IPAD.md` as the handoff guide. Reuse the guest flow and demo payment so the client can test their iPad camera and Canon SELPHY AirPrint setup. The scope ends at the deployable folder. Publishing and the physical device check are separate steps.

## 1. Add a dedicated browser build

- Add `apps/kiosk/vite.web.config.ts` and a single HTML entry with `src/renderer/web/` as the Vite root, `base: './'`, a resolved absolute `dist-web/` destination, `emptyOutDir: true`, and `build.target: 'safari16.4'`. Add `dev:web`, `build:web`, and `preview:web` in the kiosk package, add `dist-web/` to the root ignore file, and include the new TS entry and config in the relevant TypeScript projects. Test the configured root, output path and preview together.
- Mount the existing `App` from the browser entry with `auth={null}`, the existing theme and font imports, and the demo API. Install the typed browser `window.kiosk` before mounting `App` so its settings, Setup and queue effects can call it on the first render. Explicitly define `VITE_WEB` and `VITE_TRIAL` as enabled, `VITE_FAKE_API` and the three backend URL/key variables as empty for web. Suppress automatic export of unrelated `VITE_*` values from the kiosk's existing `.env`. Avoid importing `src/renderer/src/main.tsx` in the web entry so the Supabase client and Electron e2e hook bootstrap are outside the web import graph.
- `DemoKioskApi.getSettings()` currently returns `pairedPrint: true` explicitly. Add an optional demo constructor/factory setting whose default preserves that value and have the web entry pass false. The 2×6 layout still uses the existing two copies of one person's strip per 4×6 sheet through the normal non-paired composer. Keep Electron's existing build flag handling and scripts. Declare the optional `VITE_WEB` type in `env.d.ts` for intentionally shared UI branches.
- Include the Safari viewport, Home Screen and touch icon metadata in the web HTML. Use a production CSP that permits same-origin assets and workers, inline styles React needs, and `data:`/`blob:` images and media for the camera and QR. Add the CSP at build time or relax the dev HTML as needed for Vite React Refresh. Do not include third-party origins in the production policy. Use `script-src 'self'` and let Vite emit the production module as an asset.
- Add a small web artifact check using the scanning functions in `scripts/check-prod-bundle.mjs` where compatible. Its existing `assertPackageableBundle` requires Electron entry files, so use web-specific expectations: index, assets, worker, manifest and icons; the demo marker; no source maps, known test hooks, Electron entrypoints, backend hostnames or opaque key material. Check that a stray `VITE_FAKE_API=1` in the invoking shell cannot change the result. Scan leaks without printing secrets.

## 2. Implement the browser bridge and persisted state

- Under `src/renderer/src/web/`, implement an injectable IndexedDB store and a bridge typed as `KioskBridge` from `src/shared/bridge.ts`. The interface contains config, PIN, overlay, print, photos, queue and all three held-strip calls. Use one versioned app-specific database, with metadata for configuration and queue and separate blob records for overlays and photos. Keys can be `overlay:<templateId>` and `photos/<sessionId>.jpg`. Store photo timestamps and reread a JPEG by the exact validated synthetic path, never an arbitrary URL. Commit each write before resolving. Handle failed open, transactions, quota and version changes. Request `navigator.storage.persist()` whenever available as a best effort.
- The renderer runs settings caching, queue operations and Setup PIN changes concurrently. Use atomic IndexedDB read/modify/write transactions for live config and queue mutations so a settings sync cannot overwrite a PIN or lose queued jobs. Serialize the async PBKDF2 checks and updates through one service instance so parallel calls cannot race the attempt counter. Store the PIN hash as `pbkdf2$<iterations>$<saltB64>$<hashB64>` with WebCrypto SHA-256, 100,000 iterations, 16 random salt bytes and a 32-byte derived hash. Validate the encoding, supported iteration count and lengths before deriving. Use the current PIN for replacement and expose only `toConfigView`, including the real store health. Reuse `PIN_PATTERN` and `createPinThrottle` from the dependency-free `src/main/pin-throttle.ts` or move that throttle to shared with a compatibility re-export. The fifth consecutive failure starts a 30 s lock, then doubles to a 5 minute cap. A correct PIN resets it.
- Reuse `src/main/config-validation.ts` behavior by sharing its pure config validators and splitting its `Buffer`-returning PNG helper from browser-safe signature/size validation. Keep the Electron adapter and existing exports intact. Use `DEFAULT_LOCAL_CONFIG` and normalize persisted records before use. If startup cannot read/write storage, render a staff-facing error with a reload action before mounting the shared App: `App.reload` presently has no rejection path and otherwise leaves a blank loading screen. When a later write fails, surface it through the existing screen error paths and real store health where applicable. Missing records may initialize defaults. Explain that deleting site data removes settings and photos. Detect and report incomplete/corrupt records when an app marker survives. Total eviction cannot be distinguished from a fresh install.
- Put the pure queue validators, `addJobs`, `applyResult` and `syncFailureStatus` behind a shared browser-safe layer if that yields less duplication. `src/main/queue-store.ts` currently imports `photoPath` from a Node-dependent module. Use an injected deterministic path mapper and leave its Electron call signatures intact through a thin adapter. Validate UUIDs, session rows, template IDs, upload paths, and result IDs. Preserve queue dedupe, retry timestamps, attempt count and truncated errors. Keep failed/pending upload photos during the seven-day cleanup so the queue can still read them. Prune aged completed photos at startup and discard corresponding completed metadata. Record a timestamp on personal photo storage to also clean up old records that never reached queueing, provided no upload references them. Use an empty held-strip implementation if calls are unreachable with the web demo flag, or implement a single durable record with atomic claim and validated write as the design allows. Ensure the web UI never waits for held strips.
- Use browser-native blobs internally and return the existing `ArrayBuffer` API to `readPhoto`/`readOverlay`. Reuse the existing shared `buildTestPageJpeg()` from `src/shared/test-page.ts`; it already produces a 1200×1800 test sheet with a visible edge border.

## 3. Prepare sheets before someone taps Print

- Make a browser print adapter that decodes a blob URL to an image mounted before activating AirPrint, with a dedicated print layer as a sibling of the React root. Under `@media print`, hide the app shell and show only this layer with `@page { size: 4in 6in; margin: 0; }`, 4×6 dimensions and no extra margins or blank page. Prevent double activation, call `window.print()` synchronously from the button tap, and clear the layer, object URL, listener and timer on completion or error. Attach the `afterprint` handler before calling `print()`. Use the agreed 90 s fallback. Treat `afterprint`/fallback as dismissal or return to the app. A thrown print call or preparation error produces a failure result. Safari provides no confirmation that a sheet printed or whether the native dialog was cancelled.
- `Output.tsx` starts work in a React effect, and `runOutput` calls `bridge.print` after composing and saving. Bridge the handoff with an optional web print controller. It stages the JPEG as soon as `runOutput` requests it, waits for a prepared image, and resolves the existing print promise after the guest taps a dedicated button and returns from the print sheet. Keep the existing queue path and its print failure follow-up. Keep Electron wired to the current `bridge.print` call, with no new tap. On a web preparation failure, resolve the print as failed so delivery can proceed. On unmount/expiry dispose the prepared sheet and pending listeners. On `Try again` after a queue failure, preserve prior print outcome as `Output.tsx` already does. Verify one dialog for one activation. Keep the prepared image out of the print output until it is ready. A print button can remain disabled while preparing rather than prompting another tap.
- For Setup, prepare the shared test sheet when its devices screen opens, then call AirPrint directly on `Print test page` click. The current `Setup.tsx` awaits `setConfig` before `printTestPage`. Keep that sequence for Electron, but skip it on web because choosing a printer happens in the iPad sheet. Return one informational `listPrinters` entry and render a short explanation on web rather than a meaningless printer selector. Test status should say the iPad print sheet closed, without implying the paper was delivered. Set copies in AirPrint. Distinguish fallback/blocked messages from a physical printer failure, which the webpage cannot observe. In web Delivery copy, say the QR is for the trial demo and remove any claim that it downloads the guest's photo if printing fails.

## 4. Adapt camera, canvas and orientation

- `Capture.tsx` already uses `autoPlay`, `playsInline` and `muted`. Keep that path and use an ideal front facing constraint when the browser build has no exact device ID. Add a “Front camera (default)” selection to web Setup. The existing Setup selects the first enumerated device and refuses an empty choice. For web, the default stores `null` and a separately confirmed camera permission/probe lets Setup distinguish the default selection from missing hardware. Offer a visible “Enable camera” action after denial or no permission and show an actionable message for missing hardware. Close the temporary preview stream after enumeration. Handle a stale stored camera ID with a prompt to reselect it or a deliberate fallback to the default on the web path. Preserve Electron's explicit device selection.
- Check secure context, camera API, a functional 2D OffscreenCanvas, JPEG encode, image bitmap, IndexedDB and WebCrypto before entering the app. Report missing browser capabilities with an update or HTTPS message. Check actual feature availability, because minimum-version labels and UA detection cannot prove camera or canvas support. Preserve the existing Capture retry/cleanup. Verify that permission refusal and device errors present recovery instructions. iPadOS 16.4 introduced 2D OffscreenCanvas. Validate that the current composition path works on supported WebKit, and flag iPadOS 17+ as recommended until the hardware check. [WebKit Safari 16.4 notes](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/)
- `compose.ts` draws cropped photos to slots and then draws the overlay. In the web build, detect real canvas filter support before setting it. On unsupported contexts, draw each cropped photo slot, read its pixels and apply the CSS filter transforms in existing order before the overlay. Keep alpha unchanged. Preserve the native filter path and avoid get/put operations for Original. Keep preview and output on the same composition implementation. Cover deterministic pixels for grayscale weights, contrast, sepia mixing, saturation and brightness, plus values clamped at both ends. Avoid extra full-sheet bitmap allocations on the iPad.
- Import separate web CSS for safe-area insets, viewport sizing and camera touch behavior. Keep the guest flow usable at 820×1180 portrait and 1180×820 landscape iPad viewports; use responsive compositions instead of an orientation cover. Keep Setup scrollable with the on-screen keyboard open. Scope selection and overscroll restrictions to kiosk chrome, respect adequate tap targets and visible focus, and keep the app chrome out of print.

## 5. Share trial rules and make the app installable

- Move `evaluateTrial`, the state/status types and the time constants from `src/main/trial.ts` into `src/shared/trial-clock.ts`. Share the current JSON shape parser as a pure helper. Re-export the current public types/functions from the Node trial module so Windows startup and existing tests preserve the same behavior. Keep its fsync and Node-specific recovery logic in that module.
- Add a versioned browser `localStorage` key, evaluate and persist it before starting the app, then run the same check each 60 s and on resume/focus where Safari may have paused timers. Corrupt or inaccessible stored state ends the trial. Preserve 72 hours from first launch, monotonic last seen timestamp, a rollback greater than 10 min, and permanent expiry within stored data. Account for another tab's newer state via `storage` or re-reading at every check. Present the same “Trial ended” text as `src/main/trial-ended-page.ts` when expiry is reached. Unmount guest flow, stop its effects, and clean up camera/print when appropriate. Clearing all browser data can restart the local clock, and Home Screen installation may keep different data from Safari.
- Add a manifest with `name: "Photobooth Trial"`, relative scope and start URL, `display: "standalone"`, and `orientation: "any"`. Derive suitable 192/512 icons and a 180px Apple touch icon from `build/icon.png`. Include all generated assets in the browser dist and verify links with a nested base path. Check Setup and the guest flow in both iPad orientations.
- Generate the worker after Vite has emitted index, all fonts, JS/CSS and assets. Use relative scoped URLs resolved against the worker, a scope-specific cache prefix and a version derived from final asset bytes and the worker template. Precache the complete build including the manifest and icons before activation. Map matching in-scope navigation to the cached index and serve only the app's precached same-origin requests from cache. Delete obsolete caches owned by the scope after the replacement is fully installed. Allow the new worker to activate when the old booth tabs close to avoid mixing one version's HTML and another version's asset hashes. Register in secure production only, keep the worker revalidatable, and show a small staff status if offline installation fails. Document that offline operation starts after the first successful online load and worker installation.

## 6. Verify and prepare the handoff

- Kiosk Vitest coverage from the design: browser bridge against the injectable store, including async config/PIN concurrency, invalid inputs and queue retry bookkeeping. Cover print staging, synchronous `window.print()` activation, afterprint/timeout, cancellation/cleanup and open failure. Exercise trial persistence/expiry/tampering, capability messages and the pure look fallback. Reuse the existing Windows tests for the shared contracts.
- Add a separate Playwright web config and browser test directory so the current `playwright.config.ts` keeps targeting Electron e2e. Build the actual web artifact and serve it through Vite preview. On Chromium, use camera/media permissions and fake media flags with a page init script overriding `window.print`; simulate the `afterprint` event and inspect the single 1200×1800 image ready before the print call. Walk PIN Setup, test print, demo payment, capture, Warm or Black & White review, guest print and trial QR delivery. Verify retry behavior with startup online, wait for service worker control, reload with offline context and check PIN/config survive. Use WebKit with iPad portrait and landscape viewports to cover startup, responsive layout, visible controls and absence of browser errors; exercise denied camera handling if the runner supports reliable permission simulation. Browser emulation cannot verify iPadOS camera prompts, physical AirPrint or Guided Access.
- Verification commands: `pnpm --filter kiosk typecheck`, `pnpm --filter kiosk test`, `pnpm --filter kiosk build:web`, `pnpm --filter kiosk exec playwright test --config playwright.web.config.ts`, `pnpm --filter kiosk build`, `pnpm --filter kiosk build:trial`, and `pnpm --filter kiosk e2e`. Built-in browser binaries or native packaging tools may need installation. If the Windows packager cannot run on the host, run the earlier prepack trial build and guard independently and record the installer step as blocked. Confirm the production web bundle contains no secrets under both default and adverse local env inputs. Confirm app-shell loading at a subpath and complete asset loading offline.
- Add `docs/IPAD.md` and a README link. Document static `dist-web/` upload over HTTPS, setup in Safari/Home Screen, portrait and landscape orientation, Guided Access and camera permission, local storage behavior and trial expiry, demo payment, the PIN and staff setup. Include instructions to join the SELPHY network, tap **Print test page**, select the printer and the available 4×6/postcard option, and check layout, centre, crop and margins against the test's edge marks. Then run a guest session and note camera selection, look, print sheet and physical result. Collect iPad model/iPadOS, SELPHY model and paper option if anything differs. Apple requires the iPad and printer to be on the same Wi-Fi network for AirPrint. [Apple AirPrint instructions](https://support.apple.com/en-gb/109349)
- For the first handoff, make the deployable build folder available and report which verification ran. The hosting account/domain and a physical client iPad/SELPHY are still needed for a client URL and hardware signoff. Note explicitly that Safari controls paper options, borders and scaling, and that older supported iPads still need real device checks for camera, composition performance and installation data retention. The controller updates the Obsidian notes with actual evidence before handoff.
